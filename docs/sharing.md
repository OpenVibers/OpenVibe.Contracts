# Sharing on OpenVibe: core contracts

`share@1` (`contracts/share/share.v1.json`) is the uniform GET/PUT response. Resource refs are `{ service, kind, id }`; every subject is `identity.subject-ref@1`, never a local id or bare string.

| API | Request contract | Response contract |
| --- | --- | --- |
| GET /api/v1/{kind}/{id}/share | none | share@1 |
| PUT /api/v1/{kind}/{id}/share | share.update-request@1 | share@1 |
| POST .../share/requests | share.access-request-create@1 | share.access-request@1 |
| POST .../share/requests/{id}/dismiss | none (empty JSON) | share@1 |
| POST .../share/transfer | share.transfer-request@1 | share@1 |
| POST .../share/transfer/{accept,decline,cancel} | share.transfer-action-request@1 | share@1, or share.transfer@1 for a recipient's accept/decline |
| GET /api/v1/share/people?name=exact | query `name` | share.people-lookup@1 |
| GET /api/v1/shared-with-me | limit (1–100), cursor (opaque) | share.list-result@1 |

The GET/PUT body names people, not bare subjects. `owner`, every member, the pending transfer's `to` and every pending request carry `share.person@1` (`{ subject, username, display_name, avatar_url }`, from Network's identity projection; a subject Network does not know, or reports banned or deleted, has a null username). It also carries `you` (`share.you@1`: `owner` or `staff`), `requests` (pending only, `share.access-request-view@1`) and the service's own `describe(ref)`: `title`, `link`, `roles` (default `['viewer']`), `audiences` (default all four) and `transferable` (default `true`). `owner_subject` stays for ids-only consumers. PUT, POST transfer, cancel, dismiss, and a recipient's accept or decline answer with the same body and a fresh ETag so the Share sheet redraws from one shape; a recipient's accept or decline answers the plain `share.transfer@1` its banner expects.

PUT replaces members when `members` is present; omitted fields are unchanged. `name` and `subject` are mutually exclusive. Members and transfer recipients must be active **user** subjects: non-user subjects are refused, and a user subject is verified against Network's batch resolver, so unknown, banned and deleted accounts cannot be added. Names are exact, resolved by Network with per-caller rate limiting; there is no global suggestion endpoint. `GET /api/v1/share/people?name=` is signed in only, answers `{ person }` or `{ person: null }` for an unknown, banned or deleted account, and shares the name-check budget (`429 share.rate_limited`). `notify: false` on a PUT suppresses `share.added` for that save; events still flow. The agent SDK `.add()` preserves existing members.

Public is listed and viewable by anyone; link is viewable by link but excluded from listings/indexes. People admits active members; private admits the owner. Editors may edit only with people audience. An unexpired pending transfer permits its recipient to preview in any audience. Staff moderation is an authenticated server assertion and every override is audited. A staff member who is not the owner may narrow access only — set the audience to private and remove members — and nothing else; widening, adding a member or raising a role is a generic 404 like any other non-owner. A denied resource returns generic 404 with no title or content. A non-GET request without an Authorization header needs `X-Requested-With` or `Sec-Fetch-Site: same-origin|same-site`, otherwise `403 { code: 'share.csrf' }`.

Transfer actions must include `transfer_id`, preventing a stale notification from accepting a newer offer. A transfer request accepts `to` as an exact `@name`, a subject ref, `{ subject }` or `{ name }`. Only the exact recipient subject can accept/decline; only the owner can cancel. Seven-day expiry is enforced at access and action time. Accept removes the old owner's membership unless `keep_access` is true (viewer); public/link viewing remains inherent to that audience. Private becomes people when keeping the old owner as viewer, so the chosen retained access works. These operations are atomic and log outgoing/incoming ownership separately. A pending access request is `pending`, `granted` when its person is added, or `dismissed` when the owner dismisses it.

The events are `share.granted`, `share.revoked`, `share.transfer.requested`, `share.transfer.accepted`, `share.transfer.declined`. Payloads never carry titles or content in **any** audience. Network owns these shared contracts and adopting services use their own event source and declare produced types in their manifests. Audience changes, cancellation and expiry emit appropriate grant/revoke effects; notification kinds are `share.added`, `share.access_requested`, `share.transfer.requested`, `share.transfer.answered`. Only a newly added member hears `share.added` (not on a role or expiry change, and never on removal or expiry); the owner hears an answer, accept/decline/expiry, and the recipient hears a cancellation. Nobody is told about their own action, and the owner is never told about their own audience change.

Service integration must enforce `canView` on pages, raw/download/API, embeds, media proxies, comments and previews. Only public resources may be indexed, exported to search, listed in sitemaps or have content previews/events; even an owner viewing a private item must not export its content. Store media private and serve it through a checked service proxy. The SDK core does not retrofit adopting service routes.

Grant/revoke payloads may carry `reason` (member_added, member_removed, member_expired, audience_changed, transfer_cancelled, transfer_expired, ownership_changed) and `transfer_id`. A consumer removes only the indicated grant: losing a pending preview does not remove an independent membership. Audience changes update the resource-wide audience. These are access metadata, never titles or content.
